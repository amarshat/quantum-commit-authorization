**These numbers are zkSync gas, which is not the same unit as L1 gas.** zkSync charges an ergs-derived amount that folds in the pubdata cost of the transaction's state diff, so a reveal here is not comparable, digit for digit, to the L1 receipt-gas tables in `../contracts/bench`. The point of this harness is not a cheaper number. It is the existence proof: a type-0x71 transaction from `QCAAccountZkSync` validates and executes end to end on a real node, with no ECDSA anywhere on the authorization path and no ERC-4337 bundler relocating the envelope. The forge `--zksync` unit tests cannot show this because their VM does not run the bootloader / NonceHolder validation path; this does.

## Versus the ECDSA baseline

A zkSync EOA is the `DefaultAccount` system contract, which verifies a secp256k1 signature in its own validation. A plain signed transfer from an EOA is therefore the like-for-like cost of an ECDSA account authorizing the same action, and the gap to our reveal is what the zero-ECDSA machinery (membership proof, nullifier SSTORE, aging, and the account's own validation) adds on top.

| action | ECDSA DefaultAccount | QCA reveal (depth 16) | overhead |
|---|---|---|---|
| authorization only (0-value) | 118,704 | 157,923 | 1.3x |
| 1 ETH transfer | 126,763 | 174,583 | 1.4x |

The honest read is not that zero-ECDSA is cheaper. It is the same order of magnitude as a signed transfer, so the authorization can be made post-quantum without an ECDSA fallback at a bounded, small-multiple cost, on a live native-AA platform. The commit is a separate prior transaction (see the table above); this row compares the reveal against the single ECDSA transaction it replaces.

Commit is depth-independent (it stores one mapping entry). The reveal carries the Merkle proof, so it grows about 833 gas per tree level (one keccak plus the proof word), a small linear term on a large fixed base. The 1 ETH action row adds a value-bearing external call on top of the authorization-only reveal.

## What ran

Per depth and flow: deploy the account via `createAccount` (so it is registered as an AA account), fund it, post a commit, advance chain time past `minCommitAge`, then send the reveal as a type-0x71 transaction whose `customSignature` carries `(leafIndex, secret, proof, maxFeeCap, callGasFloor)`. Every reveal returned status 1. Transaction hashes are in `qca-zksync-receipts.json`; the run is deterministic (fixed secrets), so re-running reproduces the same hashes and gas.
